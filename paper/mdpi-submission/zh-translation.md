## 摘要（译）

规则治理、需证据承载的文档评审包含三个条件：明确的评审准则、可按源定位的文档，以及临时发现与可问责的人工处置之间的区分。我们提出 **HARK**——一种把评审准则表示为带 hard、hybrid、soft 操作权限的规则的架构与已执行系统。确定性校验器产生检查与候选片段；定位证据门禁检查提交的引文；确定性策略从合格发现集合推导建议结论；决策记录支撑反馈存储。技术方案是唯一的实证实例。在 100 份合成方案、253 处植入缺陷的固定开发性回归语料上，组合配置的 micro-F1 为 0.798，关键词基线为 0.222，策略结论一致率 85%。70 份策略非通过文档中 15 份被低判、10 份被判为通过，其中包括 23 份期望 Fail 中的 4 份。85 处漏检中 68 处进入待处理，但没有人类已处置的证据。三份内部方案上的五次开发团队运行展示了工作流与持久化，而非独立评审质量或学习增益。被评估的快照不强制认证式人工批准、完整有效权限上限或内容寻址的配置恢复；这些是**目标契约**而非已实现保证。本文的贡献是一个可执行的评审架构，带有有界的比较结果与显式的实现边界。

**关键词**：文档评审；评审知识表示；操作权限；证据可追溯性；确定性验证；人工处置；反馈持久化

## 1 引言

规则治理、证据承载的文档评审把三件事放在一起：组织给出的显式评审准则、可定位到源的文档、以及「临时发现」与「可问责的人工处置」的区分。检查单式评审为此提供了基础；计算问题不只是生成意见，而是表示「系统能检查哪些准则、能提供什么证据、哪些决定仍属于评审人」。

研究对象是某大型公用事业企业在线服务平台的技术方案：描述预期架构、接口、数据流、实施计划与风险的实施前文档。保证案例（assurance case）、合规档案与架构设计是同一任务表述的潜在应用，但不是本文验证过的领域。显式评审准则也出现在工程实践之外：欧盟《人工智能法案》把高风险系统的市场准入与文档化的风险管理、技术文档和合格评定绑定，使评审准则的可检视性同时成为监管问题。

**动机原型**用关键词列表与提示词表示 24 条专家规则，没有持久反馈层。这种安排难以区分「要求被提及」与「要求被满足」，也难以把一条拟议发现连到可检视的决策路径。其关键词部分在评测中由基线 B0 代表：在固定合成语料上，B0 召回 18.6% 的植入缺陷，产生 124 条假发现（真发现 47 条），策略结论一致率 κ = −0.043。这些结果说明需要另一种表示与路由架构；它们不证明是模型失败，也不隔离分型的因果贡献。

以「上线前须做负载测试」为例：「没有安排负载测试」与「负载测试计划：待定」都提到了该活动，却没有给出合格计划；反过来，「上线前将在 500 TPS 下做预生产容量演练并测量响应时间」可能提供了相关证据，却不含「负载测试」字样。这些例子区分了词面出现、文档位置与实质满足：确定性线索可以支撑有限检查或指出待审段落，但不能单独证明测试计划充分。

我们把「评审准则、证据期望与决策权限应如何进入辅助评审系统」称为**评审知识摄取问题**。关键词检查提供可复现的表面测试，提示词传递上下文指令，检索提供相关历史材料；但没有一种机制单独给出「准则—文档范围—拟议发现—处置」的完整契约。HARK 用显式规则记录与评审状态把它们组合起来，而不是把模型输出当作最终决定。

两条设计张力：其一，评审准则混合了可观察结构与语境判断（章节存在可机械检查，风险是否充分则需解释）；可验证性与路由相关，但「能执行词法测试」不能与「业务要求完全可判」混为一谈。其二，有用的决策历史可以影响后续评审，但「记录决定」「授权知识变更」「证明评审质量提升」是三件不同的事；系统必须暴露这些边界，而不是从名字推断人工批准、从存储的反馈推断学习收益。

HARK 保留原型名称，但不暗示已经验证了「人在闸门内」的保证。系统实现为通用 agent 宿主的扩展包：与宿主无关的评审引擎承载表示与决策逻辑，薄宿主集成提供存储、工具与投递。**把系统挂在宿主上是设计立场而非实现捷径**——评审系统必须规定谁可取证据、谁可提议发现、谁可提交裁决，把这些权限锚定在宿主边界上使其显式、可与评审逻辑分离；引擎模块不从宿主导入任何东西，评审语义可在任何部署之外执行与审计。

**四项贡献**：（1）规则治理、证据承载文档评审的任务表述，以及把证据生产、临时发现、建议结论与人工处置分开的规则表示（§3.1）；（2）hard/hybrid/soft 操作权限模型、校验器产出的缺失记录、引文检查与确定性结论策略，并给出这些路径在被评估快照中的边界（§3.2–3.5）；（3）与宿主无关的引擎与薄部署集成，承载反馈记录、覆盖、措辞范例与评审状态存储，并与认证式批准、完整有效权限控制、内容寻址恢复三项**目标契约**相区分（§3.6–3.8）；（4）固定合成集上的端到端回归比较、可追溯性与待处理工作量分析，以及三份内部方案五次运行的开发团队工作流证据（§4）。

**四个研究问题**：RQ1 评审知识与操作权限如何表示、实现边界在哪；RQ2 端到端配置在固定合成集上呈现怎样的检测与结论权衡；RQ3 有哪些可追溯性与门禁接受证据、多少未决工作量被转给人工；RQ4 有哪些证据支持决策持久化、人工批准与版本恢复，还缺什么。RQ2 是组合配置比较，不是分型的因果效应；RQ4 是工作流与恢复证据，不是在线改进。

图 1 给出架构：Markdown 文档被解析为可按源定位的结构；校验器产生发现或候选片段；判断者提交引文；门禁检查引文位置；确定性策略从合格发现推导建议结论；决策与反馈分开存储。在被评估的快照中，门禁检查的是「与候选片段重叠」而非严格包含，门禁确认的发现可在人工采纳前影响建议，最终结论工具只要求一个评审人字符串而非认证式批准。更严格的权限分离与完整配置恢复属于目标契约，不是已实现的保证。

## 2 相关工作（要点）

- **规则治理、证据承载的文档评审**：检查单与评审程序有长期传统；需求工程补充了质量准则、异味检测与可追溯性。本文用该术语指「组织提供评审要求、系统把拟议发现与材料中的证据关联、可问责评审人处置自动程序无法解决的议题」的任务；技术方案评审是唯一实证案例，不主张跨领域迁移已被证明。
- **需求质量与操作可验证性**：需求异味检测（弱措辞、占位符、缺单位）可支撑结构检查与候选定位，但表面线索不等于要求被满足。需求工程中的「可验证性」指能否通过适当的验证程序确立满足，**不是**当前解析器能否判定；HARK 的层级是相对于现有解析器、校验器、表示与规则包的操作性指派，不构成要求的内在质量排序。
- **LLM 辅助需求评审与评测**：已有综述与 MARV、ReqPlan-Eval 等系统提供证据使用与评审人参与的先例；被检视的材料不足以断定其文档范围校验或持久反馈的细节，因此不推断这些能力缺失。幻觉、长上下文位置效应、自纠正局限等研究针对不同失败模式，它们支持「把模型判断与签发结果的权限分开」，而不是证明 HARK 路由策略有效。
- **神经符号政策评审**：PolicyGuard 把组织政策编译为类型化关系规则，用 LLM 抽取事实、再做符号求值；其 v1 报告还记录了法律专家在评审引擎构建与验证中的细化工作。因此把它描述为「没有反馈或人工维护」并不准确；比较点应是证据生产组件的角色与评审知识的生命周期，而非一般性缺陷。Galitsky 与 Rybalov 的过程控制约束检查是另一类设置，不是设计文档评审研究。
- **工业评审与可编辑的反馈知识**：代码评审提供相邻证据（微调 vs 提示、BitsAI-CR 的双微调模型与数据飞轮、RovoDev 的部署评估、CodeRabbit 回复分析）。CodeRabbit 的 Learnings 文档（2026-11-05 访问）描述了可查看、可编辑、按角色治理删除的存储式学习，是可检视评审知识的正面先例；但它本身不证明完整历史回滚、权限上限执行或按当时知识内容重放。HARK 的存储反馈应与这些具体机制比较，而不是与一个「不透明工业 agent」的均质类别比较。
- **锚定、未检出与待处理决定**：属性生成把断言连到来源；逐条引文评测区分「引用合规」与「引文确实支持断言」。HARK 增加的是与规则关联的工具侧资格检查：定位提交的引文并检查其与该校验器候选证据的重叠。这个**定位重叠门禁**比「完整片段包含」或「语义蕴含」更窄；定位到的引文仍可能无关或被误读，候选检索也可能漏掉相关材料。校验器拥有的「未检出记录」只报告「指定程序在其声明的检查范围内未找到预期材料」，不是「要求未满足」或「文档任何表示中都不存在」的证明；模型生成的缺失断言不被接受。混合规则缺少可用候选、或发现不满足证据条件时，显式的**待处理**状态保留未决义务，而不是变成通过或确认失败。
- **人工控制、记忆与版本要求**：记录决定、授权知识变更、证明改进是不同成就；版本标识与审计记录本身不等于可恢复性。这一区分贯穿 §3.6–3.7 的目标契约。

## 3 材料与方法

### 3.1 任务表述与范围

文档为 Markdown，解析为章节、表格、图示与字符偏移，使发现可定位。规则记录包含 `id / dimension / severity / tier / verifier / rationale / suggestion / status / provenance`。评审状态区分：校验器发现、门禁确认发现、专家采纳、最终处置。任务范围限定为技术方案；保证案例、合规档案、架构设计只是潜在应用。语料为中文，规则包面向一个组织的方案评审；换语言或文档族需要新的证据映射与验证。

### 3.2 操作权限类型

- **hard**：由确定性校验器判定，可产生带位置的缺失记录（模型永远无权提交缺失证据）。
- **hybrid**：校验器定位候选片段，模型只能在片段内判断；无候选时为「待人工」，不是「未通过」。`whenNoCandidate: fail` 只允许 hard。
- **soft**：只形成待人工条目，不进入结论计算。

层级是**被评估快照中的执行路径**，不是业务要求的内在可判定性；一次成功的词法检查只证明其可观察谓词，不证明负载测试计划或安全设计的充分性。冻结规则包共 28 条：10 hard、13 hybrid、5 soft；四条 blocker 全部是 hybrid。

### 3.3 解析、校验器与业务谓词

解析器识别章节、表格、Mermaid 图示与偏移；校验器家族包括 `section / table / statement / quantity / mermaid-sequence / cross-ref`。解析器可见的谓词可能窄于业务准则（例如「要求 Mermaid」反映的是当前包可检查的格式，而不是「图片不可读即设计有缺陷」）。DOC-001、MON-001 等历史标签的边界在 §4.5 说明。

### 3.4 定位证据门禁

模型通过登记工具提交发现。门禁：拒绝 hard 规则登记；禁止模型缺失证据；检查归一化引文长度（8–300 字符）；定位引文并检查其与 hybrid 候选的关系；未知或 soft 规则提交保留为待处理。拒绝原因被存储以便检视与修复。

门禁建立的是「引文可恢复 + 位置关系」，不是「引文支持指控」：部分重叠可以通过，真实但误导的引文可以被接受。严格包含契约需要单独的边界测试与重新评测。我们不把零误报或抗提示注入归因于该门禁。报告的 42/53 是**门禁接受率**，不是语义证据有效率。

### 3.5 建议结论与最终处置

令 C 为具有合格路径（hard / hybrid / 专家）、状态为 confirmed / adopted / rewritten 的发现集合。冻结策略下，门禁确认的 hybrid 发现可在专家采纳前进入 C。以 m 为 C 中 minor 的数量、θ = 3：

- 存在 blocker → Fail；
- 否则存在 major 或 m ≥ 3 → Revise；
- 否则 → Pass。

待处理与 soft 不计；驳回的发现离开 C。意见通道的发现成为编号条款，检查单通道形成整改附件，但两条合格通道都参与策略。确定性聚合保证同一发现集可重复，不保证该集合正确；模型仍可通过被接受的登记或严重度选择影响建议。最终结论工具只要求评审人姓名字段——那是来源元数据，不是认证；agent 可以填一个名字。定稿也不可靠地要求每个待处理项都已处置。因此当前实现支持的是**可信操作员工作流**，不是软件强制的人工签名边界。

### 3.6 反馈记录与配置恢复

复核 preset 规定预审、专家处置与定稿三阶段；采纳/驳回/改写/新增成为结构化记录，统计与措辞范例可被召回。软件存储反馈，不等于后续判断会改善，也不等于记录为操作员的人真的批准了每个动作。

存储对象：`rule_overrides`（状态、严重度、建议、白名单参数、草案）、`reviews`、`issues`、`feedback`、`exemplars`、`rule_candidates`、`eval_runs`。

要求附一段原文 `basis.quote` 的严重度/状态编辑会被记录（操作员、时间、评审），但**任意足够长的字符串都能通过**，不证明同意。参数修改与有效草案激活可以在不改 tier 字段的情况下改变决策资格。Reset 删除覆盖但保留统计，却可能恢复到比上次批准更强的出厂设置。界面显示的 `pack@ver+ovN` 统计的是「被覆盖的规则数」：两个不同配置可以有同一个 N，它既不是内容身份，也不能支持精确历史重放。审计记录是有用的来源证据，但可逆性需要保留「要恢复到的实际配置」并校验其权限，而不只是删掉覆盖。

### 3.7 所需的人工批准与恢复契约（目标，未实现）

在需要「软件强制人工批准」声明的部署中，有效权限是一个元组：允许的决策主体、可采纳证据、无候选行为、严重度、适用性、激活状态与策略资格。每条写路径都必须把合并后的配置与其批准上限校验，包括参数编辑、草案激活、发现级严重度、启用/禁用与重置。

可信宿主须在向已认证评审人展示确切对象与动作后签发批准事件；事件须绑定评审/规则身份、输入与意见/配置内容、动作与取值、主体与消费/过期状态。agent 提供的名字或引文不得铸造该事件；内容变更、跨对象使用与重放使批准失效。最终签署要求显式处置待处理项，或单独授权的豁免并说明理由；界面不得把「已确认发现上的 Pass」与「评审完成」混淆。

可恢复版本要求对规则、词库、覆盖、策略及相关解析器/校验器版本做内容寻址的不可变快照，并与输入和批准记录关联；恢复须回到指定批准状态，并在固定输入上复现预期行为，同时保留审计历史。验收测试须覆盖：有效批准与伪造/缺失/重放/内容变更的批准；改权限的参数/草案/严重度/重置路径；未决项签署；部分重叠引文；以及覆盖计数相同但内容不同的配置。这些测试与修复是本文之后的工程工作。

该契约假定宿主认证、存储与受控评审 API 可信；恶意管理员，或拥有任意宿主 shell/文件写权限的 agent，超出评审层能防御的边界。缩小读取范围可以减少暴露的上下文，但不构成对提示注入、语义操纵或数据外泄的证明。

### 3.8 实现与被评估版本

HARK 作为通用对话 agent 宿主的扩展包交付；宿主提供模型访问、文件转换、结构化提问、投递、JSON 存储与 Web 服务器。**把系统挂在宿主上是刻意的设计立场而非实现捷径**：评审系统必须规定谁能取证据、谁能提议发现、谁能提交裁决，把这些权限锚定在宿主边界上使其显式、可与评审逻辑分离。引擎本身与宿主无关：parser、verifiers、gate、policy、aggregation、renderer 都是对规则包、文档与记录状态的纯函数，引擎模块不从宿主导入任何东西。扩展包定义 7 个存储对象、9 个工具、3 个状态查询斜杠命令与宿主服务的 dashboard，复用宿主认证、文件处理与投递，无独立后端、无 embedding 索引。复用使集成面很小，但**针对具体操作的批准仍是独立需求**，不能由评审人姓名字段提供。

被评估版本对应仓库快照 `b566b08de2976451747215af4dc874a0846f6173`；存储输出被重新聚合，未改输入、标签、规则或运行时行为。一个未来的规则、门禁、策略或状态机修复必须在新冻结版本下评测，这些历史检测分数不为它背书。工件提供测试套件，但**干净环境的全套复现未在此确立**：受检环境遇到宿主 peer 依赖缺失与打包忽略断言失败，因此不声称「已发布测试全通过」的计数。

## 4 结果

### 4.1 回顾性评测设置

**语料与标签**：生成器（seed 20261029）产生 100 份合成方案与 253 处植入缺陷，覆盖 23 条可验证规则：98 缺失、37 否定、52 占位、66 关键词在但内容空洞。13 份文档无植入缺陷，87 份至少一处。期望结论由冻结策略从植入缺陷导出：30 Pass、47 Revise、23 Fail。30 份策略通过文档中有 17 份含可允许的 minor 缺陷，因此「策略通过」不能当作「无缺陷」的同义词。30 份方案按 30 条历史专家意见的结论分布塑形，但它们不是原始私密文档，也不是针对生成文本的独立专家标签。

语料与短语池随规则包共同开发；自检守卫选定的执行一致性条件（包括未植入要求上的意外校验器失败），但**不要求每处植入缺陷都产生校验器失败**——植入缺陷可以保持待处理或被漏掉。生成器相关的 DOC-002 附件编号捕获修正说明其对开发的价值，也说明该语料是**开发性回归证据**，不是未被触碰的语义评审测试集。

**配置**：B0 用规则特定子串，无结构与否定处理，但施加同一聚合策略。S-full 使用校验器、候选路由、门禁与策略，判断者是确定性的 **flag judge**：候选带否定、断言型或占位线索时提议发现；它不解释设计充分性。S−verifier 把 hybrid 陈述搜索扩大到全文。B0 不调用该判断者；比较改变多个机制，不能隔离分型的因果效应。记忆存在于软件中，但这些输出不度量召回反馈的处理效应。报告语料分数未运行任何在线 LLM 配置。

**指标与出处**：按（文档，规则）对齐；从 TP/FP/FN 之和重算 micro-P/R/F1，从存储输出重算逐文档平均 F1；空真值与空预测的逐文档 F1 记为 1。重算策略结论准确率与未加权 Cohen's κ、门禁接受率、漏检转待处理率。包外新增与 soft 项不进入 23 条规则的检测分数。已发布的确定性重复产生相同核心输出，不提供独立样本。分析是重新聚合存储记录，不重新生成语料、不重跑引擎；统计量是描述性的，不作推断。文档是观测单位；253 处缺陷或 2300 个规则—文档对都不是独立文档样本。

### 4.3 可追溯性与待处理工作量（RQ3）

85 处漏检中 68 处落在待处理的 hybrid 文档—规则对上（80% 转交覆盖率），17 处未被自动路径抬升。**转交不是恢复**：存储结果不显示评审人读到了该项、识别了缺陷或改正了结论。完整待处理集含 932 个唯一 hybrid 对，每文档均值 9.32、中位数 9、范围 6–13（不含 soft 项）；其中 68 对与植入缺陷重合（7.3% 标签密度）。其余对不能称为假阳性——待处理表达的是不确定，不是断言缺陷；该密度也不是评审时间的度量。

### 4.4 结论错误与阈值敏感性

S-full 与 S−verifier 在这些输出上完全相同：扩大区域没有为这个线索驱动判断者暴露差异，不能据此确立「对生成式判断者限定范围」的效果。

|---|---:|---:|---:|
| Pass | 30 | 0 | 0 |
| Revise | 6 | 41 | 0 |
| Fail | 4 | 5 | 14 |

70 份策略非通过文档中 15 份被低判（21.4%），10 份被判 Pass（14.3%）：6 份期望 Revise、4 份期望 Fail。23 份期望 Fail 中 4 份被判 Pass（17.4%），9 份得到非 Fail 建议（39.1%）。40 条建议 Pass 中 10 条相对策略标签是错的（25%）。13 份真正零缺陷文档全部无发现；另有 17 份文档虽有 minor 植入缺陷但策略判 Pass。这些分母既防止夸大「干净文档」表现，也防止把「通过文档上的所有缺陷」都当成误放行。

### 4.5 历史样例及其标签边界

生成方案 `syn-hist-30` 涉及向第三方渠道开放的余额查询能力。三条门禁确认的 blocker：占位式并发控制（CAP-001）、被否定的绑定关系检查（SEC-002）、占位式暴露风险评估（SEC-004）；第四条确认发现是 hard 图示规则 DOC-001，MON-001 保持待处理。存储的期望与建议结论都是 Fail，逐文档 F1 为 0.889。该语料案例中的自动 hybrid 行为者是 flag judge，不是 LLM。

其中两部分不能解释为独立业务缺陷证据：DOC-001 在冻结的 Mermaid 谓词下让「仅图片图示」失败，却不评估图片内容；MON-001 把「须补充新页面追踪点以统计使用」视为缺少实施陈述，而对建设前方案，这可能正是需要评审完整性的实施计划——「尚未完成部署」不自动构成方案缺陷。保留这些历史标签是为了与分析版本一致，同时指出任务/标签不一致；在把修正后的谓词当作已验证之前，需要领域负责人裁决与新的冻结评测。

### 4.6 开发团队工作流证据（RQ4）

作者报告在三份私密技术方案上的五次运行（一份修改后再审、一次恢复运行），只有两次评审到达最终结论。这些运行共 58 条发现：40 条校验器定位、12 条模型判断、6 条操作员新增；12 条模型判断中 3 条因候选外引文被拒。还报告 18 个决定（15 采纳、3 驳回、0 改写）、13 条规则的统计与 21 条措辞范例。这些类别描述的是作者的工作流记录，不是对私密存储的重建审计，也不是独立专家研究；私密源文档、模型/提示配置与完整批准/决策轨迹无法在此独立核验。

该记录支持「普通操作员主导使用中反馈可被记录与聚合」的可行性，不支持「每条记录都有已验证同意」「待处理项必然被处置」「工作量下降」「独立评审人接受度」或「学习曲线」；也不修复 §3.7 描述的可调用接口与配置恢复反例。要更强的工作流证据，需要一条匿名轨迹，把输入、门禁结果、处置与有效配置绑定到每份最终意见，同时不公开机密内容。

## 5 讨论

- **RQ1**：HARK 把评审准则做成带证据期望与操作路径的可检视规则记录。规则包 10 hard、13 hybrid、5 soft，四条 blocker 全为 hybrid；层级标示本包中的执行路径，不是业务要求的内在可判定性。设计区分了校验器发现、门禁确认发现、专家采纳与最终处置；被评估快照实现了其中一部分，但**未强制完整的目标权限契约**：门禁确认的 blocker 已能影响建议结论，部分 hybrid 结构失败由校验器直接产生。
- **RQ2**：S-full 相对 B0 的 micro-F1 从 0.222 升至 0.798（差 0.576），配对逐方案 F1 差 0.564（不同聚合）。这是在开发性合成回归语料上的有界改进；B0 与 S-full 在检测器、线索处理、候选路由与证据检查上都不同，B0 也不使用 flag judge，因此比较不隔离分型的因果效应。S-full 与 S−verifier 相同只说明该确定性判断者未暴露「扩大片段范围」的效应。结论权衡是单边的但并不良性：85% 一致率下，70 份非通过文档中 15 份被低判、10 份被判 Pass（6 份 Revise、4 份 Fail）。
- **RQ3**：flag judge 提交 53 条，42 条过门禁，11 条因引文长度不足被拒；79.2% 是门禁接受率，不是语义证据有效率。43 条 hybrid 真阳性 = 42 条门禁接受 + 1 条结构性直接失败。当前位置谓词检查与候选片段的**重叠**；重叠与真实引文都不证明文本支持指控。85 处漏检中 68 处进入待处理、17 处未浮出；932 个待处理对中只有 68 个与植入缺陷重合，该密度不是待处理项精确率。基于合格发现的建议 Pass 不等于完成评审。
- **RQ4**：三份内部文档、五次运行、两次到达最终结论，提供工作流证据；58 条发现与后续统计描述的是被记录的活动，不是独立审计的质量或学习增益。决策记录可以被持久化与聚合，但不证明来源已认证或能改进后续评审。最终结论路径接受评审人字符串，部分编辑的指令引文只做长度检查；待处理发现可以在定稿时保留。权限与恢复缺口不止于 tier 编辑：无候选行为、草案激活、发现级严重度与重置都能在不改 tier 的情况下改变有效决策行为；`pack@ver+ovN` 只计数被覆盖的规则，不同行为可共享同一标签。认证式、绑定动作与有效内容的批准，对所有改权限操作的控制，以及不可变配置快照，都是目标契约。

**对证据承载评审的启示**：有用的抽象是「把准则、证据对象、操作路径与处置连起来的评审记录」；它使建议的输入可检视，但不把可检视当作正确。人工批准仍是设计要求，其工程实现必须与普通操作员工作流区分。同一抽象可以支持保证案例、合规档案或架构设计，但每种都需要领域特定的证据对象、生命周期假设、规则来源与处置责任；本文未验证这些应用。缩小模型输入也不能消除提示注入或反馈存储的隐私风险。

## 6 局限与未来工作

- **开发性合成评测**：语料复用短语池、与规则包共同开发；植入标签与期望结论反映生成器与同一策略；自检是执行一致性检查，允许植入缺陷保持待处理或被漏掉。因此比较是回归结果，不是语义评审准确率的独立估计。文档是重采样单位；253 处缺陷与 2300 个规则—文档对不是独立文档样本；逐字节相同的确定性重复不增加抽样证据。统计量为描述性，不声称置信区间或显著性检验。泛化需要冻结开发工件与独立标注、来源分离的材料。
- **判断者与组件归因**：flag judge 对校验器线索作出反应，不解释设计意图；其召回与精确率既不是 LLM 的一般下界也不是上界。端到端比较改变多个组件，不识别分型的单独效应。未报告跨模型稳定性、门禁的语义蕴含或生成式判断者的片段范围收益。
- **人工批准与有效权限**：被评估实现假定可信的操作员工作流；它不通过评审人名或指令引文字段认证人工批准；待处理议题可以在定稿后保留；现有限制不覆盖参数修改、草案激活、发现级严重度与重置等完整有效权限面。更严格的实现需要把批准绑定到可信主体、动作、对象、有效内容与消费状态，并对待处理项显式处置或豁免。这些控制是计划中的，未在此实现或验证；其缺失限制保证性主张，但不意味着内部运行中有滥用。
- **版本恢复与反馈使用**：覆盖计数版本标签是显示摘要，不是唯一内容标识；它不能单独复现过去评审，也不能区分覆盖数相同的不同配置。目标恢复契约要求把有效规则、词库、覆盖、策略、解析器与校验器版本及审计游标保存为不可变快照。当前持久化与聚合证据不证明完整历史重放、每次更新的认证归属或反馈的净收益；不作纵向改进主张。
- **领域、生命周期与输入覆盖**：28 条中文规则包面向一个组织的技术方案评审；hard 指快照的自动路径，可能使用比业务准则更窄的词法或结构代理。当前包要求 Mermaid 反映的是解析器可见检查；没有格式要求时，图片不可读本身不证明设计有缺陷。未来时态的实施计划应按方案阶段准则判断，而不是当作未通过的实施验收。改变这些谓词、标签、层级或证据规则需要重新验证，受影响处需重算；当前指标不能转用于修订后的任务。其他语言与文档族需要各自的证据映射与验证。
- **工作流证据与人因**：三份内部文档、五次运行、仅两次到达最终结论，不足以确立外部评审人接受度、工作量下降或更好的决定；报告计数不是对私密试点存储的独立审计。待处理转交不是人类解决，建议与最终结论的一致也不是橡皮图章的直接度量。人工处置质量、时间成本、漏掉的待处理项与自动化偏差仍未测量；评估这些结果必须区分「临时建议」与「评审完成」。

## 7 结论

HARK 通过显式准则、操作权限路径、定位证据、临时发现与决策记录来表示规则治理、证据承载的文档评审。技术方案是唯一实证实例；保证案例、合规档案与架构设计仍是潜在应用。系统的贡献是这些评审对象与接口的可执行组合，而不是「模型、校验器或记录的操作员名字能确立可问责的最终决定」的保证。

在固定合成回归语料上，组合配置 micro-F1 0.798（B0 为 0.222），TP/FP/FN = 168/0/85；策略结论一致率 85%，70 份非通过文档中 15 份被低判（含 10 份建议 Pass、23 份期望 Fail 中 4 份 Fail→Pass）；68 处漏检进入待处理，但没有人类已处置的证据。开发团队运行支持工作流与反馈持久化，不支持独立质量或在线学习收益。认证式批准、完整有效权限上限与内容寻址恢复仍是未实现的目标契约。这些边界界定了当前设计与验证证据所能支持的范围。
